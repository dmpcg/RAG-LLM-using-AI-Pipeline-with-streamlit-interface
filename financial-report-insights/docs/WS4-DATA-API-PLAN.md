## 3. Work packages (grouped by file for wave parallelism)

### WP-LLM — local_llm.py resilience (P0-11, P0-14, P1-C2, P1-C4, P1-C1-stream-timeout)  *(M, ~4.5h)*
- **P0-11:** add `close()` to `LocalEmbedder` (closes `self._client`); register `atexit` OR implement `__enter__/__exit__`; ensure idempotent. Test: `close()` closes the httpx client; double-close safe.
- **P0-14:** `import random`; add `random.uniform(0, wait*0.25)` jitter to the embedding retry backoff (`_send_embedding_batch`) and the LLM retry path; keep determinism testable by allowing a seeded/injected RNG or asserting the sleep arg is within `[wait, wait*1.25)`. Test: jittered wait within bounds.
- **P1-C2 (encapsulation, NOT a race fix):** add public `record_success()`/`record_failure()` to `CircuitBreaker` whose bodies ARE the existing `_on_success`/`_on_failure` logic (which already acquire `self._lock` internally); keep `_on_success`/`_on_failure` as thin aliases or rename in place. Have `generate_stream` (:287,:289) call the PUBLIC methods. **DO NOT** wrap these calls in `self._lock` at the call site — `self._lock` is a plain non-reentrant `threading.Lock` (:56) and the method bodies re-acquire it, so an outer acquire DEADLOCKS. `call()` itself does NOT hold the lock when invoking these (its `with self._lock` ends at :135). Test: streaming success/failure updates breaker state via the public methods; assert NO deadlock (call records back-to-back); do NOT assert a pre-existing race (none exists — state mutation was already individually locked).
- **P1-C4:** add explicit `raise RuntimeError("unreachable: retry loop exhausted")` after the `_send_embedding_batch` retry loop (signature contract; defends against a future edit to the loop that drops a return). Acknowledged: with current bodies this terminal raise is unreachable (every last-attempt branch already raises), so the "never implicitly returns None" test only proves the guard exists. Test: (a) drive the loop with `max_retries=0` (or monkeypatch the loop bound to 0) so the body never executes → assert the terminal `RuntimeError` fires (the one truly reachable implicit-None path); (b) ADD a real-failure-mode test the original objection flagged — when `data['data']` is an empty list (:533) the function returns `[]` and embeddings silently go missing; assert this case at minimum logs a warning (do not change the return contract). Both tests are within local_llm.py.
- **P1-C1-stream-timeout (owns the `local_llm.py` half of P1-C1 — resolves clarity C3/C6):** pass a finite read timeout to the streaming `ollama.generate(model=..., prompt=..., stream=True)` call at `local_llm.py:296` (via `timeout=settings.llm_timeout_seconds` on the call or its underlying httpx client) so the blocked C-level socket read can unblock and the orphaned `to_thread` worker/connection is reclaimed. This is the ONLY edit that genuinely caps the thread leak; the `api.py` `wait_for` (WP-API-RES P1-C1) bounds client-side latency only. Test (in local_llm.py): the streaming generate path carries a finite read timeout (assert on the call kwargs / client timeout config).
- **Risk:** atexit during interpreter shutdown — guard close() against already-closed. **Serialize:** all FIVE are in local_llm.py (one agent), so local_llm.py is FULLY owned by WP-LLM in Wave 1 — WP-API-RES (Wave 2) touches api.py only, no cross-wave edit to local_llm.py.

### WP-RERANK — reranker.py (P1-A3, P1-D6)  *(M, ~3h)*
- **P1-A3:** cache doc embeddings on the reranker instance keyed on a **content hash** (`hashlib.sha256(content)`), NOT id-only — `documents` dicts are not guaranteed to carry a `chunk_id` (`rerank` reads only `'content'` at :68), and an id-only key would collide when two chunks share an id but differ in text (stale-content bug). Key = content-hash; if a `chunk_id` is present, use `(chunk_id, content-hash)` so a content change under the same id is still a cache miss. **Bound the cache:** use an `OrderedDict` (or `functools.lru_cache`-style) with an explicit max size (reuse the LLM-cache pattern, `settings.llm_cache_maxsize` or a new `settings.reranker_cache_maxsize`, default 1024) and LRU-evict — the cache lives on a long-lived reranker instance and MUST NOT grow unbounded across distinct queries/corpora. Only embed cache-misses each `rerank()`. Note the existing `try/except` (:94-96) returns original order on ANY embed failure — keep that; on a partial-miss embed failure, do NOT poison the cache (only insert on success). Tests: (a) second rerank() of overlapping docs issues embed only for new docs (spy `embed_batch` call args); (b) **collision test** — two docs with the same content but different text-after-edit produce distinct cache entries (no stale reuse); (c) cache size never exceeds the configured bound after many distinct docs (LRU eviction).
- **P1-D6:** integration test with `settings.enable_reranking=True` that **spies on `EmbeddingReranker.rerank`** and asserts (1) it WAS invoked AND (2) `retrieve()`'s returned ordering equals the reranker's output (i.e. its result was actually used). Asserting only on `retrieve()`'s return is VACUOUS: the activation site (`app_local.py:929-935`) wraps the reranker in `try/except Exception: logger.debug(...)` and falls through to the UN-reranked results, so a thrown construction/rerank error is swallowed and the original order flows through — a return-only assertion passes even when reranking silently failed. Also add a negative test: when `rerank` raises, `retrieve()` still returns (graceful) AND the swallow is logged. Test-only.
- **Risk:** cache staleness under same id — mitigated by content-hash keying; unbounded growth — mitigated by the bounded LRU above.

### WP-API-RES — api.py resilience (P1-C1, P1-C5, P1-C6, P1-C7)  *(M, ~5h)*  [serial on api.py]
- **P1-C1:** wrap the per-chunk `await asyncio.to_thread(next, it, done_sentinel)` (`:300`) in `asyncio.wait_for(..., timeout=settings.llm_timeout_seconds)` (CORRECTED setting name — `ollama_timeout_seconds` does NOT exist; config defines `llm_timeout_seconds` at config.py:51); on timeout, emit an SSE error event and stop cleanly. **Documented limitation (be honest in the test name + docstring):** `wait_for` cancels only the awaiting coroutine — it does NOT cancel the worker thread that `to_thread` dispatched; that thread is blocked on a C-level socket read inside `ollama.generate(stream=True)` (local_llm.py:296) and keeps running until the OS/TCP layer returns, orphaning one default-executor worker and holding the upstream connection. This fix bounds CLIENT-SIDE latency (SSE returns promptly) only; it does NOT reclaim the thread/connection. To genuinely cap the leak, the streaming client also needs a finite httpx read timeout — that `local_llm.py:296` edit is **OWNED BY WP-LLM (P1-C1-stream-timeout, Wave 1)**; WP-API-RES edits api.py ONLY. Tests (api.py-only): (1) a hung *async* chunk source times out and the stream closes with an SSE error event (no indefinite block) — name it `..._client_side_timeout` so it is NOT mistaken for thread cancellation. (The finite-read-timeout assertion lives in WP-LLM, not here.)
- **P1-C5 (CORRECTED — reorder is a no-op; the real fix is a cross-IP sweep):** prune ALREADY precedes append at :217, so "reorder before append" fixes nothing. The dead lines are :224-226 (`if not _rate_log[client_ip]: del` right after an append — never empty). Replace them with a periodic **cross-IP sweep**: on each request (under `_rate_lock`), drop every IP whose entire pruned list is empty — e.g. `for ip in [k for k,v in _rate_log.items() if not [t for t in v if t > cutoff]]: del _rate_log[ip]` (or sweep only when `len(_rate_log)` crosses a soft threshold to bound per-request cost). This is what actually evicts an IP that stopped sending; a single-IP path cannot (the `defaultdict` re-creates the key on touch). Keep the existing 10K hard-cap clear (:227-229) as a backstop. Tests: (1) an IP that sent requests, then all its timestamps expire, IS removed from `_rate_log` after a later request from ANY IP triggers the sweep; (2) the 10K hard cap still clears; (3) an active IP within the window is NOT evicted.
- **P1-C6:** catch `LLMConnectionError` → 503 BEFORE the generic `except Exception` → 422. **Two cases:**
  - analyze (:320-361), export_xlsx (:626-635), export_pdf (:653-664) ALREADY wrap the analyzer call inside the 422 try — just add an `except LLMConnectionError -> 503` ahead of `except Exception`.
  - portfolio_analyze (:761), portfolio_correlation (:789), compliance_analyze (:833) wrap ONLY `_parse_financial_data`; the analyzer calls (`pa.full_portfolio_analysis` :773, `pa.correlation_matrix` :801, `cs.full_compliance_report` :845) run OUTSIDE any try, so catching there NEVER fires (LLMConnectionError becomes an unhandled 500). For these three, **WIDEN the try** to enclose the analyzer call (keeping the parse-error path → 422), then add `except LLMConnectionError -> 503`. Take care not to convert genuine bad-input ValueErrors into 503.
  - Tests: injected `LLMConnectionError` yields **503** (not 422, not 500) for /analyze, /export/xlsx, /export/pdf, /portfolio/analyze, /portfolio/correlation, /compliance/analyze; a malformed-input payload still yields 422 for all six.
- **P1-C7:** add `limit: int = Query(100)`, `offset: int = Query(0)`, `source: str | None = Query(None)` to `list_documents` (`:923`); apply filter+slice. Test: pagination params slice/filter correctly; defaults unchanged.
- **Serialize:** all in api.py.
